# 승인 대기 점검 (Phase 종료용)

세션이 느리게 느껴질 때 줄여야 할 것은 대개 테스트가 아니라 **승인 대기**다.
이 스킬은 그것을 **추측이 아니라 트랜스크립트를 세어서** 처리한다.
(출처: kanadic 프로젝트에서 개발, 2026-08-19 — 본문의 실측 수치는 그 프로젝트 것이다.)

## 언제 부르는가

- **Phase 종료 시.** 단 **셸 호출이 100건 이상 쌓였을 때만** 의미가 있다 —
  짧은 구간의 노이즈에 규칙을 맞추면 규칙만 늘고 효과는 없다. 스크립트가 이 조건을 강제한다
  (미달이면 exit 2로 멈춘다. `--sessions N`으로 이전 세션을 합칠 수 있다).
- **사용자 호출 전용이다.** 설정을 바꾸는 일을 알아서 시작하지 않는다.

## 절차

### 1. 측정

```bash
python scripts/measure_approvals.py
```

여러 세션을 합치려면 `--sessions 3`. 특정 세션은 `--session <ID 또는 경로>`.

**호출이 0건으로 나오면 '깨끗함'이 아니라 실패다** — 트랜스크립트 형식이 바뀌었거나 엉뚱한
파일을 본 것이다. 스크립트가 실패로 끝내니 그 메시지를 그대로 사용자에게 전한다.

### 2. 원인을 갈라서 읽는다 — 여기가 이 스킬의 핵심이다

보고서는 원인을 다섯 갈래로 나눈다. **처방이 서로 다르다**:

| 분류 | 처방 | 규칙을 넣는가 |
|---|---|---|
| **형태** (`cd <루트> &&` 등) | 호출 방식을 고친다. 반복되면 **PreToolUse 훅**으로 강제 | ✗ |
| **셸제어문** (`for`/`do`/`done`) | 셸 루프를 **파이썬으로** 옮긴다 | ✗ |
| **읽기전용** (grep·sed·wc…) | `settings.json`의 `allow`에 추가 | ✓ |
| **상태변경** (rm·tar·pip…) | **아무것도 하지 않는다** — 묻는 것이 맞다 | ✗ |
| **판단필요** | 사람이 본다. 기본값은 "안 연다" | 사용자 확인 후 |

> **★ 이 표가 있는 이유**: "승인 요청을 줄인다"는 목표는 구조적으로 허용 목록을 넓히는 쪽으로
> 기운다. 이 템플릿은 정반대 조항을 갖고 있다(CLAUDE.md '허용 목록을 넓히지 않는다').
> kanadic 2026-08-19 실측에서 최대 원인(154회)은 **규칙이 아니라 내 호출 습관**이었다 —
> 규칙만 늘렸으면 3분의 1도 못 줄였다.

보고서의 `[시나리오] A/B/C`가 처방별 효과를 나눠 보여준다. **B(호출 형태만 고침)가 이미 크게
줄면 규칙을 넣을 이유가 그만큼 줄어든다.**

### 3. 처방을 사용자에게 제안하고 확인받는다

- 제안은 **읽기 전용 규칙**과 **호출 습관/훅**으로 나눠서 낸다.
- `[자동 제안하지 않음]` 목록은 **줄이자고 제안하지 않는다.** 필요하면 사용자가 먼저 말한다.
- 파일 조회로 쓴 필터(`← 파일 조회다` 표시)는 규칙이 아니라 **`Read`/`Grep`/`Glob` 도구로
  바꿀 자리**다. 규칙을 넣는 것은 파이프 뒷단(`flutter test | tail -3`)을 위해서다.

### 4. 반영

- 규칙: `.claude/settings.json`의 `permissions.allow`. **`settings.local.json`도 함께 본다** —
  거기 쌓인 규칙이 있으면 project 쪽만 고쳐도 효과가 달라 보인다.
- 훅: `.claude/hooks/no_redundant_cd.py`는 **이미 동봉·등록돼 있다**(settings.json의 hooks —
  경로는 `$CLAUDE_PROJECT_DIR` 변수를 쓴다. 훅이 안 도는 것 같으면 그 변수가 해석되는지부터
  확인하고, 안 되면 절대 경로로 바꾼다). 새 훅을 만들면 **반례까지 파이프 테스트하고 넣는다**
  (`no_redundant_cd`는 `cd app` 단독 호출을 막으면 안 된다 — 테스트에 반례가 있다).
- 습관: CLAUDE.md의 '작업 속도 규칙'에 한 줄. **다만 문서로 안 막히면 훅으로 옮긴다** —
  `cd` 함정은 문서에 두 곳이나 적혀 있었는데도 한 세션에서 154회 반복됐다.

### 5. 검증 — 스크립트를 고쳤다면

`python -m pytest tests/test_measure_approvals.py`

이 분석기는 **죽지 않고 그럴듯하게 틀리는** 종류의 코드다(실제로 두 번 그랬다:
따옴표 안 파이프를 세어 건수가 부풀려짐 / `cd` 패턴 하나를 명령·조각에 같이 써서 "0건"이라는
거짓 결과). 로직을 건드렸으면 **변이를 하나 넣어 테스트가 실패하는 것을 본다.**

### 6. 커밋

```bash
git commit -F .commit_msg.txt
```

커밋 메시지에는 **원인별 건수와 시나리오 수치**를 남긴다. 다음에 같은 작업을 할 때
비교 기준이 된다.

### 7. ★ 마무리 — 두 가지를 반드시 한다

1. **규칙 반영을 그 자리에서 재검증한다** — 실제로 묻던 명령으로. 즉시 적용 여부는 실측이
   갈렸으므로(노하우 문서 '로드 시점' 참조) 단정하지 말고, **판정은 `settings.local.json`에
   그 명령이 새로 적히는지로** 한다. 계속 새로 쌓이면 그때 세션 재시작을 요청한다.
2. **보고서의 수치는 예측이지 실측이 아니다** — 양쪽으로 틀린 실사례가 있다(과대·과소).
   → **`scripts/measure_wait.py`로 벽시계를 재서 닫는다** (`--grep <명령>`으로 전후 비교).
   확인이 이 세션에서 안 끝났으면 인계 메모(`work_log/plan.md`)에 남긴다.
