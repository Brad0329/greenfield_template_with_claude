# 신규(Greenfield) 시스템 개발 — AI 코딩 스타터 템플릿

완전히 새로운 시스템을 처음부터 만드는 프로젝트를 Claude Code로 진행할 때
**첫날부터 장착하고 시작하는** 템플릿.

레거시 재구축 템플릿(`legacy-template-with-ai-coding`)의 자매판 — 원본 대조/데이터 이관 장치를
걷어내고, 그 자리에 **요구사항 명세를 기준점**으로 하는 장치를 넣었다.

**스택 중립적이다.** 웹·앱·CLI·라이브러리 어디에도 쓸 수 있게 특정 스택의 명령·경로를 넣지 않았다.
빈칸은 초기화 때 채운다.

## 사용법

1. 새 프로젝트 루트에 이 폴더 내용을 복사한다(`.claude/`는 숨김 폴더라 빠지기 쉽다).
2. Claude Code에서 그 폴더를 열고 **이렇게 말한다**:

   ```
   새 프로젝트 시작하자. 초기화부터 하자.
   <프로젝트 이름> — <한 줄 설명>. 스택은 <스택>으로 갈 생각이다.
   ```

   `CLAUDE.md`는 자동으로 읽히고, `<...>` 플레이스홀더가 남아 있으면 **초기화 체크리스트를 먼저
   진행**하게 되어 있다. **이 README를 읽으라고 시킬 필요는 없다** — 사람이 읽는 문서이고,
   초기화 마지막 단계에서 지운다.
3. 못 채우는 칸은 지우지 말고 "미정"으로 남긴다 — 나중에 그 결정을 해야 한다는 표시가 된다.

```
CLAUDE.md                        ← 규칙·정책. 초기화 체크리스트 내장
docs/REQUIREMENTS.md             ← 요구사항 단일 원본 (제일 먼저 채울 것)
docs/SCHEMA.md                   ← 스키마 변경 결정 기록 + 승인 게이트
docs/playbooks/_TEMPLATE.md      ← 사고 1건 = 파일 1개
work_log/plan.md                 ← 전체 계획 단일 원본
work_log/_TEMPLATE_Phase_XXX.md  ← Phase 완료 로그
.claude/agents/*.md              ← 선택적 검증 에이전트 3종
.claude/settings.json            ← deny(안전장치)만 채워져 있다. allow는 비어 있다
```

## ★ 초기화 때 반드시 하는 것

**`.claude/settings.json`의 `allow`를 이 프로젝트의 실제 명령으로 채운다.**
일부러 비워뒀다 — **틀린 기본값은 빈 칸보다 나쁘다.** 안 맞는 허용 목록은 매 명령마다
사용자에게 확인을 묻게 만들고, 그게 며칠간 이어진다.

- 규칙 문법: `"Bash(git log*)"` = 프리픽스 매칭, `"Bash(npm test)"` = 정확 일치. `deny`가 우선.
- **`cd X && ...` 복합 명령이나 `FOO=bar cmd` 접두사는 규칙에 안 걸린다.**
  환경변수는 `settings.json`의 `env`에 두고, `cd`는 애초에 쓰지 않는다(작업 디렉토리는 유지된다).
- `.claude/settings.json` = git 커밋(공통) · `.claude/settings.local.json` = gitignore(개인).
- `defaultMode: "acceptEdits"` 포함 — 혼자 작업 기준. **팀이면 이 줄을 개인 설정으로 옮길 것.**
- 며칠 써본 뒤 `/fewer-permission-prompts`로 실사용 기반 갱신.

## 지식 3분할 원칙 (어디에 뭘 기록하나)

| 위치 | 내용 |
|---|---|
| **CLAUDE.md** | 매 작업마다 지켜야 할 규칙·정책·함정 목록. 짧게, 링크 위주 |
| **docs/REQUIREMENTS.md** | 기능 요구사항 + 수용 기준의 단일 원본 (+ ID 대장은 CLAUDE.md) |
| **docs/SCHEMA.md** | 스키마 변경 **결정**과 이유, 승인 게이트 (현재 상태는 코드가 정답) |
| **work_log/plan.md** | 전체 계획·Phase 체크리스트·**보류 항목**의 단일 원본 |
| **work_log/Phase_XXX.md** | "코드에서 알 수 없는 것만" — 결정 이유·외부 제약·**실패한 접근**·운영 주의점 |
| **docs/playbooks/*.md** | 증상→원인→해결 상세. 사고 한 번 = 파일 하나 |
| **개인 메모리** | 접속정보, 개인 노하우 — **git에 안 들어가는 것** |

- **비밀정보(키·토큰·비밀번호)는 git·CLAUDE.md·채팅에 절대 넣지 않는다.** `.env` + gitignore.
- 사고를 겪으면: 플레이북 작성 → CLAUDE.md 함정 목록에 한 줄 + 링크.
- **요구사항이 바뀌면 그 자리에서 REQUIREMENTS.md를 고친다** — 대화 속 합의로만 남기면
  다음 세션이 구버전으로 구현한다.

## 검증 에이전트 3종 — 있으면 쓰고, 없으면 대체한다

| 에이전트 | 시점 | 역할 |
|---|---|---|
| `requirements-analyst` | 구현 **전** | 요구사항을 구현 가능한 스펙으로 + **모호점을 질문 목록으로** |
| `spec-checker` | 완료 **후** | 구현 vs 수용 기준 대조, 누락·조용한 축소·임의 추가 검출 |
| `qa-tester` | Phase 완료 | 통합 테스트 게이트(foreground). 코드를 고치지 않고 판정만 |

**환경에 따라 서브에이전트 호출이 안 될 수 있다.** 그때는 CLAUDE.md '검증 게이트' 표의
대체 수단으로 가되, **검증 자체를 건너뛰지 않고 그 사실을 작업 로그에 남긴다.**

## Phase 사이클

```
plan.md에서 Phase 확인 → 수용 기준 확정(REQUIREMENTS.md) → 구현
→ 전체 테스트 통과 → 수용 기준 대조 → (가능하면 /code-review)
→ plan.md 체크 [x] + Phase_XXX.md 작성 → 다음 Phase
```

**가장 위험한 것을 먼저 한다.** 쉬운 것부터 하면 나중에 못 하는 걸 발견한다.

## 기본 탑재된 함정 목록

1. **요구사항 없이 구현 시작** — "만들다 보면 알겠지"는 스코프 크리프의 시작
2. **과잉 설계(YAGNI)** — 아직 없는 요구사항을 위한 추상화 금지
3. **Silent failure** — 조용히 삼킨 예외는 "0건 처리"를 "정상 완료"로 둔갑시킨다
4. **조용한 절단** — 결과를 자르면 잘랐다는 사실과 전체 건수를 함께 준다
5. **무단 스키마 변경** — 되돌리기 비싸다. SCHEMA.md 기록 + 사용자 확인 후
6. **템플릿 기본값을 그대로 쓰기** — 이 프로젝트 것이 아니다. 초기화 때 갈아엎는다
7. **손으로 만든 데이터** — 사람이 쓴 매핑·목록은 반드시 틀린다. 자동 검증을 붙인다
8. **통과했다고 검증된 게 아니다** — 새 테스트는 일부러 틀리게 해서 실패를 한 번 본다
9. **"됐다"를 빌드 성공으로 판단** — 화면·응답·데이터로 확인한다
10. **환경별 설정 통째 복사** — 값이 다르다. 필요한 키만 한 줄씩
