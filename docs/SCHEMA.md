# <프로젝트명> 데이터 모델 — 스키마 변경 결정 기록

> **AI는 임의로 컬럼 추가/변경, 마이그레이션 수정을 하지 않는다.**
> 스키마 변경 절차: ① 변경안을 이 문서 '변경 이력'에 먼저 기록 → ② 사용자 확인 → ③ 모델/마이그레이션 반영
> → ④ **구버전 저장본을 실제로 읽어 마이그레이션 실측 + 되돌리기 경로(백업·롤백) 확인 + 사용자 실테스트**
> 후 배포 (일반 트랙 검증 갈래, CLAUDE.md '검증 강도'). 새 코드로 만든 빈 DB는 통과하고 옛 DB만 깨진다.
> 컬럼 목록 등 상세 명세는 손으로 관리하지 말고 모델에서 자동 생성 권장(`<예: scripts/generate_schema_doc.py>`).
> 이 문서는 "결정과 이유"를, 코드(models/migrations)는 "현재 상태"를 담당한다.

## 설계 원칙

## 핵심 엔티티와 관계
- <엔티티 목록 + 관계 한 줄씩. 예: Member 1—N Order, Order 1—N OrderItem>
- <ERD 이미지/도구 링크가 있으면 여기>

## 도메인별 설계 결정
### <도메인명>
- **결정**: <예: 주문 상태는 enum 컬럼 1개로, 상태 이력은 별도 테이블>
- **이유**: <왜 이렇게 했는지 — 다음 세션이 뒤집지 않도록>
- **버린 대안**: <예: 상태별 boolean 컬럼 — 조합 폭발로 기각>
