# 노하우: 승인 대기 최소화 (Claude Code 허용 규칙 공학)

> 출처: hanjadic 프로젝트 실측(2026-08). 한 세션 23.4분에서 테스트 총합은 30초, **승인 대기가 약 6분**이었다.
> 세션이 느리다고 느껴지면 **테스트가 아니라 확인 요청부터 잰다** — 테스트 389건을 반으로 줄여도 6초 절약일 뿐이다.

## 병목 측정법

- **측정 도구가 동봉돼 있다** — `scripts/measure_wait.py`: tool_use↔tool_result 타임스탬프
  간격으로 **호출별 벽시계 시간**을 낸다. `--grep <명령>`으로 **같은 호출의 전후를 비교**하는
  것이 가장 확실하다 — 절대값에는 명령 자체 시간이 섞인다
  (실측: pytest 52.2초 → 36.7초, 실행 자체는 32초 — 차이가 대기였다).
- `scripts/measure_approvals.py`(원인 분류)는 **예측**이고 양쪽으로 틀린 실사례가 있다
  (git 과대·자기 자신 과소) — 어디를 볼지 고르는 데만 쓴다.
- 승인 대기는 상한이 없다: 실행 12초짜리 테스트가 벽시계 156.3초까지 늘어난 실측이 있다.
- **★ 벽시계만으로는 "확인 창이 떴는지"를 못 가른다** — 사용자가 2초 만에 누르면 정상 실행과
  구분되지 않는다(이 오귀인으로 판정을 두 번 뒤집은 실사례). **판정은 `settings.local.json`에
  그 명령이 새로 적혔는지로** 한다 — 사용자가 "항상 허용"을 누르면 뜬 것은 반드시 거기 적힌다.
  단 그 파일에는 **이전 세션 항목도 섞여 있다** — "적혀 있다"가 아니라 "이번에 새로 적혔다"로 본다.

## 허용 규칙 작성법

1. **규칙을 추측하지 말 것.** 사용자가 확인 창에서 **"다시 묻지 않기"를 한 번 고르게** 한다 —
   매칭을 수행하는 그 코드가 `settings.local.json`에 정확한 패턴을 적는다. 그게 정답이고,
   공용으로 쓸 것은 그 항목을 `settings.json`으로 옮긴다. (추측한 규칙으로 두 번 틀린 실측.)
2. **★ PowerShell의 `명령 *` 와일드카드 규칙은 (이 환경에서) 안 걸린다 — 정확 일치만 걸린다**
   (hanjadic 2026-08-20 실측: `PowerShell(flutter test *)`가 있는데 `flutter test --help`가
   물었다 — 슬래시도 경로도 따옴표도 복합도 없는 형태다. 정확 일치 `flutter analyze`는 통과).
   - 그러므로 PowerShell `명령 *` 규칙을 새로 넣는 것은 대개 헛수고다. **대신 호출 문자열을
     고정하는 것이 실효다** — 출력을 자르려고 `2>&1 | Select-String`을 덧붙이거나 인자를 매번
     바꾸면 그때마다 새 프롬프트다. 출력이 길면 그냥 받는다.
   - ~~종전 지침 "패턴은 `명령`과 `명령 *` 두 형태를 함께"~~ → **그 실측이 틀렸었다.** 근거로
     쓴 명령(`git status` 등)이 규칙 없이도 안 묻는 자동 허용 부류였다.
   - **★ Bash 도구도 같다** (2026-08-20 추가 실측): `Bash(.venv/Scripts/python.exe *)`가
     있는데 `--version` 호출이 물었다. **와일드카드는 두 도구 모두 무효다**(독립 사례 5건).
     그래서 이 템플릿의 allow는 **정확 일치 최소 셋**만 담는다.
   - **무효 규칙은 지운다 — 지우기는 안전하다.** 규칙을 빼면 확인이 늘 뿐이다(무효면 무변화,
     혹시 유효했다면 확인 한 번 추가). **넣을 때가 위험하고 뺄 때는 안전하다** — 신중함의
     방향이 반대다. 출처 프로젝트는 이 원칙으로 allow 101 → 35로 걷어냈다. 지운 뒤 자주 쓰는
     형태를 정확 일치로 넣고, **정리 직후 실제로 안 묻는 것을 확인**한다("지웠으니 됐다" 금지).
   - **deny가 막아 줄 것이라고 가정하지 말 것.** deny도 전부 와일드카드라 무효일 가능성이
     있지만, 시험하려면 파괴적 명령을 실제로 던져야 해서 확인되지 않았다(지우지도 않는다 —
     확인 못 한 안전장치는 남긴다). **파괴적 명령은 규칙이 아니라 부르지 않는 것으로 막는다.**
3. **`Bash(...)`와 `PowerShell(...)` 규칙은 별개다.** 이 환경의 기본 셸 도구가 무엇인지 먼저
   확인한다. Bash 규칙만 있는 상태에서 PowerShell 호출 733회가 전부 확인을 물은 실측이 있다.
   - **★ 규칙이 걸리는지 검증할 때 읽기 전용 명령을 쓰지 말 것**: `git status`·`git log`·
     `Set-Location`·`Get-Content`류는 **규칙과 무관하게 자동 허용**된다. 이걸로 실험하면 어떤
     규칙을 넣어도 "걸렸다"가 나온다 — 위 오귀인의 원인. **검증은 실제로 묻던 명령으로 한다.**
4. **자동 승인이 위험한 명령은 인자를 필수로 건다.** 예: `dart format *`(인자 필수)로 등록하면
   대상 없는 맨몸 실행(폴더 전체 포맷)은 계속 확인을 묻는다 — 안전망을 남기는 방법.
5. `deny`가 `allow`보다 우선한다. deny 목록도 셸 도구별로 넣어야 한다.

## 규칙에 안 걸리는 호출 형태 (피할 것) — 명령 앞에 무엇도 붙이지 않는다

- **`cd X && ...` / `Set-Location X; ...` 복합 명령** — 접두사 규칙을 통과하지 못해 매번
  확인을 문다. 50세션에서 이 형태 223회 = 그만큼 확인 요청(최대 원인이었다).
  → `cd`/`Set-Location`을 **한 번 따로** 부르고, 다음 명령은 맨몸으로. 작업 디렉토리는 호출 사이에 유지된다.
  - ⚠️ **단, 아래 '파이프·복합의 실제 검사 방식' 참조** — PowerShell 도구에서 앞머리가 규칙에
    걸리는 복합은 반대로 **통째로 통과**한다(2026-08-20 실측으로 종전 서술이 정정됨).
    복합 명령을 피하는 규칙 자체는 그대로 유지한다 — 이유가 바뀌었을 뿐이다.
- **환경변수 접두사(`FOO=bar cmd`)** — 같은 이유로 안 걸린다. `settings.json`의 `env`에 둔다.
- **변수 대입 접두사(`$p = "..."; cmd ...`)** — 역시 안 걸린다. **규칙이 있어도 소용없다 —
  호출 형태의 문제다** (실측: `curl.exe *` 규칙이 있는데도 변수 대입을 앞에 붙여 승인을 물었다).
  → 경로는 리터럴로 통째로 쓰거나, `settings.json`의 `env`에 정의한 `$env:변수`를 쓴다.

## ★★ 파이프·복합의 실제 검사 방식 — 그리고 우회하지 않는다 (2026-08-20 실측, hanjadic)

앞머리를 `git log`로 고정하고 꼬리만 바꾼 실험:

| | 명령 | 결과 |
|---|---|---|
| T1 | `git log \| Select-String …` | 안 물음 |
| T2 | `git log \| Out-File <경로>` | **안 물음** (파일을 쓰는 cmdlet인데도) |
| T3 | `git log --oneline -1; Copy-Item …` | **안 물음** |
| T4 | `Copy-Item …` (혼자) | **물음** |

T3과 T4가 같은 명령인데 갈린다 — **PowerShell 도구에서는 앞머리가 줄 전체를 결정하고,
`|`·`;` 뒤의 조각은 검사되지 않는다.** 여기서 따라 나오는 것:

- **파이프 꼬리용 규칙(Select-String·Select-Object 등)은 넣어도 효과가 없다** — 꼬리가
  자동 허용인지는 애초에 "관측되지 않는 값"이다.
- **★ 이것을 확인 요청을 줄이는 수단으로 쓰지 말 것.** 확인 절차는 사용자가 이 에이전트의
  동작을 통제하는 장치다. 허용된 명령을 앞에 붙여 뒤엣것을 통과시키는 습관이 들면 장치가
  무력해지고, **사용자는 자기가 승인한 것만 돌았다고 오해하게 된다.** 명령은 있는 그대로
  부르고, 물으면 물리는 대로 둔다. **속도보다 이쪽이 우선이다.**
- 그래서 복합 명령을 피하는 규칙은 그대로 유지한다 — "안 걸려서"가 아니라 **"앞머리 하나로
  뒤엣것까지 통째로 걸려 버려서"** 다. 승인 이력을 믿을 수 있으려면 한 호출 = 한 명령이어야 한다.
- **범위 제한: PowerShell 도구에서만 잰 것이다.** 같은 날 Bash 도구의 `;` 복합은 앞머리가
  규칙에 없자 그대로 물었다 — **재보지 않았으면 도구 간에 일반화하지 말 것.**

## 작업 디렉토리의 실제 동작 (실측 — 추측하지 말 것)

| `cd` 대상 | 결과 |
|---|---|
| 작업 트리 **안** (`cd app`) | **유지된다.** 다음 호출도 거기서 돈다 |
| 작업 트리 **밖** (다른 저장소) | **거부되고 루트로 리셋** — "Shell cwd was reset to…" |

- 그러므로 **`cd app && flutter test` 같은 복합 명령이 필요 없다** — `cd app` 한 줄,
  `flutter test` 한 줄로 나누면 둘 다 평범한 접두사 규칙에 걸린다.
- **유지되기 때문에 생기는 반대쪽 위험 — 드리프트.** 하위 디렉토리에 들어간 것을 잊고 루트용
  명령을 부르면 **에러가 아니라 조용히 다른 일을 한다**(`pytest tests/`가 하위의 tests를 보고
  "0건 통과", `git add -A`가 그 하위만 담김). "에러 나면 알게 된다"는 에러가 나는 명령에만
  통한다. → 하위 디렉토리에는 그 작업 묶음일 때만 들어가고 **끝나면 즉시 돌아온다.**
- **메타 교훈**: 이 표는 "매 호출마다 리셋된다"는 틀린 일반화(트리 밖에서만 뜨는 리셋 메시지를
  전체 규칙으로 착각)를 실측으로 바로잡은 것이다. 그 오해 위에 "복합 명령용 규칙을 열자"는
  잘못된 제안까지 갔었다 — **동작을 확인하지 않고 추측하면 설정을 엉뚱하게 넓히게 된다.**

## settings.json의 로드 시점과 두 파일

- **도중에 고친 규칙이 그 세션에 걸리는지는 실측이 갈렸다 — 단정하지 말 것.**
  kanadic(2026-08-18)은 "도중 수정 미적용"을 겪었고(이 오진에 한나절), hanjadic(2026-08-20)은
  "즉시 걸린다"고 결론냈다가 **같은 날 근거를 취소**했다(36.3→4.3초의 원인은 규칙이 아니라
  사용자의 "항상 허용" 클릭이었다). 어느 쪽이든:
  - **재시작 대기를 기본값으로 삼지 않는다** — "다음 세션에 확인"이 반복 지연되는 비용이 실재한다.
    규칙을 고쳤으면 **그 자리에서, 실제로 묻던 명령으로** 바로 재검증한다.
  - **판정은 `settings.local.json`에 그 명령이 새로 적히는지로** 한다(위 '병목 측정법' 참조).
    허용됐어야 할 명령이 정확 일치 형태로 **계속 새로 쌓이면** 이 세션에 로드되지 않은 것이다 —
    그때 재시작을 요청한다.
- **규칙을 닫을 때는 `settings.json`과 `settings.local.json` 두 파일을 함께 본다** —
  local에 같은 규칙이 쌓여 있으면 그쪽이 계속 연다(실측: local에서 8건이 더 나왔다).
- **`git -C <경로>`** — cwd에 안 흔들리지만 **접두사 허용 규칙에서 의도적으로 제외**된다
  (규칙을 넣어도 물었다, 실측). `Set-Location` + 맨몸 git이 유일하게 확인 없이 도는 조합.
- **공백 없는 경로를 따옴표로 감싸기** — `git commit -F "경로"`는 `git commit -F *` 규칙에 안
  걸려 18.5초 대기(같은 시점 다른 git 명령은 0.7초). Bash에서 몸에 익은 습관이 비용이 된다.
- **변수·표현식으로 시작하는 명령** — `& (Join-Path $env:LOCALAPPDATA …)` 형태는 명령이
  리터럴로 시작하지 않아 **어떤 허용 규칙에도 안 걸린다**(실측 대기 77.8초, 실행 자체는 2~5초).
  PATH에 없는 도구(adb 등)는 **전체 경로를 글자 그대로** 쓰고, 그 리터럴 경로로 규칙을 등록한다.

## 여러 줄 커밋 메시지

- here-string/인라인으로 넘기지 말 것 — 따옴표 든 여러 줄 문자열이 네이티브 exe 인자 전달에서
  쪼개져 `pathspec` 오류가 난다(한 세션에서 두 번).
- **메시지를 파일에 쓰고 `git commit -F <파일>`** 로 넘긴다.
- **그 파일 경로는 저장소 루트의 `.commit_msg.txt`로 고정한다** (gitignore 대상 — 템플릿
  `.gitignore`에 이미 있다). 임시폴더에 매번 다른 이름을 쓰면 "다시 묻지 않기"가 그 정확한
  경로에만 등록돼 다음 커밋에 안 걸린다. 경로를 고정하면 승인 한 번으로 영구히 끝난다.
- **`.git/` 안에 두지 말 것** (실측으로 두 번 옮긴 끝의 결론): 경로 고정은 맞았지만
  **`Write`가 `.git/`에 쓸 때마다 확인을 물었다** — 실측 137.1초(일반 위치 Write는 0.1초).
  허용 규칙으로 뚫으려 하기보다 **보호 디렉토리를 피하는 쪽이 확실하다.**
  루트 고정 파일 + gitignore 형태는 사용자 확정을 받았다("안 떴다", 2026-08-19).

## 무엇을 열고 무엇을 남기나 — 기준은 빈도 × 위험

**자주 부르는데 위험이 낮은 것만 연다.** 드물거나 위험한 것은 확인을 남긴다 —
확인 비용은 `빈도 × 대기시간`이므로, 패키지당 한 번뿐인 명령은 확인을 물어도 싸다.

템플릿의 `settings.json` allow에는 **정확 일치 최소 셋**만 들어 있다 — 웹 도구
`WebSearch`/`WebFetch`(셸 규칙과 매처가 다르다), 커밋 메시지 파일 `Write`/`Edit`, git 기본,
flutter/pytest의 맨몸 호출 형태. **셸 규칙은 와일드카드가 무효라 정확 일치만 실효가 있기
때문이다.** 자주 쓰는 호출이 새로 생기면 "다시 묻지 않기"로 정확 일치를 쌓아 간다.
**초기화 때 이 스택에 없는 항목은 지운다.**

**열지 말 것** (빈도가 낮아 확인 비용이 싸고, 위험은 있음):
- **패키지 설치**(`pip install`·`flutter pub add`·`npm install`) — 공급망 위험. 건별 확인 유지.
- **다운받은 실행물(스크립트·바이너리)의 실행** — 데이터 다운로드와 구분할 것.
  받은 코드를 돌리는 것은 계속 사람이 본다.
- 삭제류·`git push --force` 등은 deny에 있다(셸 도구별로 둘 다).

## 훅으로 강제하기 — 문서로 안 막히면 구조로

문서에 두 곳 적힌 함정이 한 세션에서 154회 반복된 실측이 있다. **반복되는 호출 습관은
PreToolUse 훅으로 막는다.** 템플릿에 3종이 동봉·등록돼 있다:

| 훅 | matcher | 막는 것 |
|---|---|---|
| `no_redundant_cd` | Bash | `cd <저장소 루트> && …` 접두사 |
| `no_output_filter` | PowerShell | `2>&1`·`\| Select-String/Select-Object` 출력 자르기 — **자르려다 3~7배**(209초 vs 맨몸 27.4초) |
| `no_targeted_flutter_test` | PowerShell | `flutter test <인자>` — 전체(23~27초)가 파일 하나(158~206초)보다 싸다. Flutter 없으면 삭제 |

훅 설계 규범 (전부 실측에서 나온 것):
- **반례를 테스트에 넣는다** — 맨몸·정상 호출까지 막으면 고칠 방법이 없어진다.
- **등록 직후 막히는 것과 정상 호출이 통과하는 것을 둘 다 확인한다.**
- **재보지 않은 것을 막지 않는다**(YAGNI) — 문제가 관측된 형태만 막는다.
- **훅은 재시작 없이 즉시 적용된다** (실측 — 허용 규칙과 달리 이건 확인됐다).
- 훅이 고장 나면 막지 않고 통과시킨다 — 훅 결함이 도구 사용을 봉쇄하면 안 된다.
- 그 형태가 정말 필요하면 **사용자에게 말하고 승인을 받는다. 훅을 우회하지 않는다.**
- **예외를 열 때는 "문자열이 고정인가"로 판단한다.** `flutter test --reporter failures-only`
  한 형태만 훅 예외 + 정확 일치 규칙으로 열었다(출력 68KB → 실패만 남는다) — 고정 문자열이라
  프롬프트를 새로 만들지 않기 때문이다. `--reporter <아무거나>`처럼 가변으로 열면 다시 매번
  달라진다. **예외를 늘리지 않고, 연 예외의 반례(다른 값·추가 인자·앞뒤 덧붙임)를 테스트에 넣는다.**

**효과 검증은 "작업이 쉬웠나"가 아니라 "호출 형태가 바뀌었나"로 본다.** 훅 도입 뒤 한 기능이
확인 요청 0건으로 끝나자 "간단해서였나"가 의심됐는데, 같은 트랜스크립트에서 세어 보니 파일 지정
호출 23회는 전부 훅 이전이고 그 기능은 맨몸 15회만 썼다 — 작업이 아니라 호출 형태가 달라진 것이다.

**디렉토리 승인은 별개 항목이다.** 프로젝트 밖 디렉토리(예: `~/.claude/projects/`)를 읽는 호출은
명령 규칙과 무관하게 **세션당 한 번** 묻는다(실측: 파일명이 매번 달라도 첫 건만 6.2초, 이후 9건
0.4초). 측정기를 돌릴 때 첫 호출의 대기는 이것이다 — 규칙 문제로 오진하지 말 것.

**출력이 크면 그냥 받는다** — 하네스가 큰 출력을 파일로 떨궈 주고 경로를 알려 주므로
`Read`/`Grep`으로 보면 된다. 값 하나만 필요하면 파이썬 한 줄로 계산해 출력한다.
(`2>&1`은 어차피 불필요하다 — stderr는 이미 함께 돌아온다.)

## 주의

- **작업 디렉토리 유지를 100% 믿지 말 것** — 여러 호출을 잘 넘긴 뒤 중간에 초기화된 실측이 있다.
  relative 명령이 "찾을 수 없다"류로 죽으면 cwd부터 의심하고 `cd`/`Set-Location`을 다시 부른다
  (증상이 원인을 안 가린다 — 경로를 못 찾자 엉뚱한 모듈 오류로 해석된 사례).
- 며칠 써 본 뒤 `/fewer-permission-prompts`로 실사용 기반 갱신.
